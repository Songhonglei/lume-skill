# 生成案例的编写与审查

生成任务只创建草稿。结构校验通过表示配置、文件引用和固定工具接受该结构，不表示输入没有歧义或判分条件正确。逐案审查后保存并启用，再手动评测。

## 四项检查

1. **输入完整。** 明确点名目标 Skill，写清任务、实际数据及其起止位置，区分指令和数据。空字符串、缺失字段、空格、换行分别说明；不要用“处理以下文本”代替实际输入。
2. **预期有依据。** 依据当前 Skill 的明确约定，不为未定义行为编造结果；数量不足时保留数量提示，不复制案例凑数。
3. **断言足够。** 检查完整关键结果和失败条件，保留大小写、标点、空白约定。规则不能只验证有回复或固定前缀；脚本应拒绝错误结果；语义裁判应有可观察的标准。
4. **附件自包含。** 文件已提供并正确引用，不依赖个人电脑上的路径和外部服务；答案、golden 和判分依据不放入被测会话可见的 context 或 repo_fixture。

检查不自动改写案例，也不构成强制勾选门槛。系统不会根据提示词自动判定案例质量。草稿和保存版本均可查看这份清单；复杂条件继续使用源码编辑，保留未知字段。

## 空输入的正反例

以合成 label-text Skill 为例，其约定是空文本输出 `LABEL: (empty)`。

含糊的任务描述：

> 请给以下文本加标签：

这可能被理解为忘记提供文本，要求补充输入也是合理反应。先修正任务描述，不能把断言放宽成只要求输出 `LABEL:`。

明确的任务描述：

> 请使用 label-text Skill 处理。实际输入（JSON 字符串）：""；解码后长度 0，不是缺少输入，不要请求补充文本。只输出处理结果。

完整匹配的规则示例（Go 正则，YAML 单引号保留反斜杠）：

```yaml
judge:
  type: rule_based
  success:
    - output_matches:
        all: ['\ALABEL: \(empty\)\z']
```

该规则接受 `LABEL: (empty)`，拒绝 `LABEL: wrong`、缺失内容和额外解释。如果 Skill 允许末尾换行，应按约定显式调整；不要为某次失败随意放宽条件。没有定义空字符串行为的 Skill，应先澄清约定或选择有依据的场景。

## 审查后复跑

保留原始失败报告。只澄清输入时，将修订保存为新版本，保持判分条件，之后手动发起新任务。确认正确 Skill 可以通过、错误行为会被拒绝；一次通过不能证明全部场景或所有模型都稳定。

生成完成页面、案例编辑器和结构校验结果都会提示上述边界。编写指令由应用补充，固定 skill-upper 第三方资产不修改；skill-up 0.14.0 / Codex CLI 0.162.1 保持不变。
