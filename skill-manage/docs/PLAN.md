# 自托管 Skill 注册、审计与修复平台：首期方案

更新日期：2026-10-23

状态：首期 P0–P6 已完成，当前版本 0.3.1；真实模型审计、授权修复、独立复审、新版本登记，以及 Linux 原生/Compose 完整闭环均已验证。实现、证据与覆盖边界见开发计划及 VALIDATION.md；尚未对外发布。

配套文档：[开发计划](DEVELOPMENT-PLAN.md)、[通用审计能力迁移清单](AUDIT-CAPABILITY-MAP.md)。本次修订将 CLI 安装设置与 Docker Compose 并列为正式交付路径，外接 worker 改用一次性授权码。

## 1. 定位与范围

为个人与小团队提供可自托管的一站式 Skill 注册、审计和修复平台。

首期完整链路：上传本地 Skill 或填写下载 URL → 注册不可变版本 → 审计 → 选择问题并授权修复 → 生成候选 → 独立复审 → 通过后形成可用新版本 → 下载。

自动修复属于首期必交付范围。评测、用户自定义 SkillHub、自定义 SSO/鉴权、组织多租户与分布式集群均不在首期范围。

完全移除内部 Multica、天玑、SkillHub、REDoc、Cowork/Edith SSO、内部 PyPI、CDN、埋点及财务专用规则依赖。上线/发布在首期指发布到本平台的本地 Skill 库，不代表发布到外部 Hub 或安装至 Agent。

“本地库优先”在方案中落实为两点：应用使用 SQLite 与本地文件存储；代码在本项目建立干净的本地 Git 仓库，远端创建和公开推送另行确认。

## 2. 产品主链路

### 2.1 Skill 注册与版本

- Web 支持 ZIP 上传、目录选择上传及公开 HTTP(S) ZIP 下载地址；不假设所有网页链接都是下载地址。
- 首期 URL 支持明确的包下载链接（包括仓库 archive / release asset）。普通网页地址给出可理解的提示，不偷偷抓取网页当成包。私有 URL 凭据与任意 Git 仓库认证留待后续。
- 自动解析 SKILL.md 中的名称、描述、版本；缺失字段才要求补充。导入本身不要求包已经满足审计标准，必要元数据缺失可在注册表记录并进入修复。
- 内容摘要作为包身份；名称、声明版本与平台版本 ID 分开保存。同名同版本同内容复用；同版本不同内容要求新版本或保留为候选，不覆盖原包。
- 保存来源地址、获取时间、包摘要及文件清单。再次访问变化的 URL 视为新导入，不能改变旧审计对象。
- 限制上传大小、解包后大小和文件数量，阻断路径穿越及危险链接；URL 获取校验解析地址与每次重定向，默认禁止回环、私网、链路本地和云元数据地址，避免下载器访问部署机内部资源。

### 2.2 审计

- 使用随项目分发的 skill-deep-audit 规则作为基础，去除财务专属指标及内部 Hub 红线逻辑。
- 默认 L1 静态审计；L2 由用户选择，仅进行允许的只读检查。Hub 未接入时明确显示未校验项及原因，不制造已验证结果。
- 输出结构化 JSON 和可阅读 Markdown：规则 ID、严重性、文件位置、证据、建议、分项分数、总分、实际满分、未确认项。
- 确定性检查由程序完成；语义分析由 Agent 执行。服务端依据规则证据重新核算分数与结论，不能只相信模型输出的 PASS。
- 检查未完成、输出格式错误或执行器不可用显示“未完成/待处理”，不伪装成完整审计通过。规则定义允许的跳过项单独列出。
- 审计绑定包摘要、规则版本、审计深度、执行器/模型标识与运行 ID，后续规则更新不改写历史结果。

### 2.3 自动修复与独立复审

流程：审计未通过 → 用户选择问题（默认选 ERR）并确认修复范围 → 原版本只读保留 → 隔离副本修复 → 生成差异与候选包 → 新会话独立复审 → 通过后登记新版本。

- 用户一次授权可覆盖所选问题的修复、检查和复审，不在每轮重复弹窗。
- 默认最多 3 轮；仍失败、需要业务决策、修复越界或结果无法确认时停止，保留差异、日志和未解决问题。
- 修复 Agent 可以修改授权候选目录中的脚本和文档；不运行被审 Skill 的真实业务写入，不获得平台管理员权限。
- 审计会话不能接受修复者的自评作为证据；可以由同一个 worker、同一个模型开启独立会话完成复审，不要求多 Agent 平台。
- 复审按候选最终字节执行；版本号和元数据修正必须在复审前完成。复审后修改任意包文件都会使对应结论失效。
- 成功后候选成为本平台的新版本；原版本保留，可切换当前可用版本。失败候选可查看、下载，但不能标记为审核通过。
- 默认复审通过后自动登记为新版本；任务发起时可选择“仅生成候选”，无需引入复杂审批流。
- 同一 Skill 同时只允许一个有效修复任务，防止两个任务覆盖彼此版本。

### 2.4 Web 页面

沿用现有管理应用中有效的交互与布局，整理为四个主要入口：

1. Skill 库：导入、搜索、维护者、当前版本、审计状态与主要操作。
2. Skill 详情：版本、文件、审计报告、问题、修复差异与历史。
3. 任务中心：审计/修复/复审统一队列，进度、日志、停止、重试。
4. 设置：用户、worker、模型、存储与备份。

移除财务术语、内部平台链接、RFA 单号、内部团队/项目配置、外部发布状态与评测入口。详情页优先展示当前问题和下一步，同一 Skill 的审计与修复上下文集中展示。

## 3. 架构与本地存储

默认结构：浏览器 → FastAPI Web/API → SQLite + 本地持久目录；独立 worker 通过应用 API 领取任务、下载固定包并回传结果，worker 不直接打开数据库。

- 保留 Python/FastAPI，前端沿用原生 HTML/JS，按功能拆分，首期不全面换框架。
- SQLite 保存用户、Skill、版本、审计、修复、任务、租约和事件；文件目录保存包、报告、大日志及备份。
- SQLite 采用 WAL、短事务、唯一约束和原子条件更新；原 PG 的 advisory lock、JSONB 查询、FOR UPDATE 不能直接照搬，需重写并验证。
- Web 服务为数据库唯一访问边界；任务执行在事务之外。默认单 Web 实例、单 worker、执行并发 1，首期面向单机个人/小团队。
- 首期只实现 SQLite，不提供 PG/MySQL 驱动、配置选项或兼容承诺，也不增加 Redis、独立消息队列和对象存储。
- 数据卷必须在部署机本地磁盘，不把 SQLite WAL 数据库放在共享网络盘。
- 备份通过 SQLite 一致性备份机制协调包文件清单，提供导出/恢复命令；不能只复制运行中的单个 .db 文件。
- 存储操作集中在持久层，版本迁移有编号；未来再评估 PostgreSQL/MySQL，不为尚未实现的数据库提前增加复杂抽象。

## 4. 独立 worker 与 Agent 执行器

worker 是独立进程，可与 Web 一起启动，也可在用户本机单独启动并连接平台。

职责：领取任务、心跳续租、准备隔离目录、调用审计/修复执行器、上传产物、回传状态。原 Multica 的 Issue、小队、队长和 Agent 绑定均被删除。

任务包含 attemptId、租约代次、幂等键和固定包摘要。领取与最终提交由 API 原子校验；过期 worker 的迟到结果不能覆盖新任务。允许失败后的再次尝试，但不承诺外部模型调用只发生一次。新版本登记与产物接收必须幂等。

worker 重启后根据持久状态恢复；超时任务由服务端判定过期，再生成新尝试。停止任务应终止受控子进程并保留已产生的诊断资料，不能仅在 UI 改状态。

首期默认实现内置 Agent 执行器：通过兼容的模型 API 调用模型，提供受约束的文件读取、候选编辑与检查工具。管理员配置 endpoint、model 与凭据，onboard 实测工具调用和结构化输出能力；不能假定任意“兼容接口”均可完成修复。可连接用户自托管的兼容模型服务。

静态检查不需要模型；语义审计和自动修复需要可用模型。没有配置时平台仍能注册和查看 Skill，但对应任务明确等待配置，不用模拟执行冒充闭环。未来可新增 CLI 执行器，首期不同时承诺兼容全部 Agent CLI。

两种部署均提供独立任务目录：原包只读，候选目录可写。Agent 只能使用服务端定义的文件工具和固定检查器，不能获得任意 shell、eval/exec、任意 Python 执行或安装包能力；不能运行目标业务脚本及其测试/构建钩子。所有路径校验含真实路径和符号链接边界，模型凭据由受控执行层使用，不写入候选目录或传入模型上下文。

CLI 原生模式不以 Docker 为必装条件，使用上述受约束工具完成完整审计/编辑/复审；这是工具权限隔离，不声称达到容器或虚拟机级隔离。Compose 使用独立 worker 容器，不挂载宿主用户目录、Docker socket 或平台数据库。未来若支持任意代码行为测试，必须另设执行隔离方案；首期不以审计为名执行未知业务代码。固定语法检查器只能解析目标内容，不能加载其模块或运行其插件。

## 5. 简化身份与权限

首期采用本地账号、密码和服务端会话，不接公司 SSO。密码散列、会话失效、写请求防伪造和基础登录限速仍属于最小实现。

| 操作 | 管理员 | 普通维护者 |
| --- | --- | --- |
| 浏览平台 Skill 与报告 | 全部 | 全部（首期采用共享库） |
| 新建 Skill | 可以 | 可以，自动成为维护者 |
| 上传版本、审计、修复、版本切换 | 全部 | 仅自己维护的 Skill |
| 调整归属、管理用户、设置模型与 worker | 可以 | 不可以 |
| 停止任务 | 全部 | 自己有维护权限的 Skill |

首期每个 Skill 一名维护者；账号由管理员创建，不开放公共注册。未来再扩展协作者与私有可见性。

worker 使用独立机器凭据，只能领取分配任务和提交产物，不能操作用户管理。默认部署自动配对；外接 worker 采用一次性授权码：

1. 管理员在“添加 worker”生成授权码，默认 10 分钟有效、仅可兑换一次。
2. 用户运行 CLI 的 worker join，填写平台地址并粘贴授权码；授权码默认通过隐藏输入接收，不放入命令行参数、URL 或日志。
3. 平台在事务中校验并消费授权码，登记 worker，签发仅用于 worker API 的机器凭据；CLI 自动保存至权限受限的本地配置，随后启动即可接单。

平台只存授权码/机器凭据的校验摘要，兑换接口限速。管理员可撤销未使用码、停用 worker 或吊销机器凭据；一码并发兑换只允许一个成功。授权码不是后续心跳用的长期凭据。平台地址为必要连接信息，不要求用户手填工作区 ID、项目 ID 或 API Key；非回环连接要求 HTTPS。

兑换响应丢失时不得重新使用已消费的码；页面可查看未上线登记并撤销后生成新码。尚未成功本地保存凭据的 worker 不领取任务，避免遗留登记产生实际执行。凭据轮换和重新接入行为须有明确状态提示。

## 6. skill-deep-audit 集成方式

已读取上游 SKILL.md、README 与 LICENSE：当前文档声明 1.1.0、MIT，7 维度，L1 满分 117、L2 满分 120，统一通过线 90 分且零 ERR。

上游是 Agent Skill，不是完整后台审计程序。上游交互版要求先选深度、修复分级授权、修复后再次确认复审。平台需要提供明确的自动化执行契约，而不是直接照搬后让后台等待聊天回复。

计划将上游 Skill 作为本项目一部分随版本分发：

- 固定到经审阅的上游 commit，保留 MIT LICENSE、来源、版本和本地修改记录，不在任务执行时下载 main 最新版。
- 保留通用规则、参考材料与路径检查器；新增平台调用适配，接收任务中已确认的深度、修复范围和自动复审授权。
- 在平台适配版中明确上述交互差异，避免声称未经修改的上游已原生支持全自动闭环。
- 输出报告存入任务产物区，不写进最终 Skill 包；内部逻辑不使用旧财务 150/120 评分。
- 保留不确定项与误报复核证据；模型参与的语义结论不承诺绝对确定性。

## 7. 一键部署与 onboard

Docker Compose 和 CLI 原生安装是首期两条同等验收的路径，使用同一 Python 包、规则版本、配置模型和数据库迁移，不能分别维护业务实现。

| 路径 | 安装与设置 | 启停与运维 |
| --- | --- | --- |
| Docker Compose | 提供 compose.yaml 与固定版本镜像/源码构建入口，自动建卷、建库和内置 worker 配对；Web onboard 创建管理员和配置模型 | Compose 启停；CLI 可在 Web 容器内执行诊断、备份与恢复 |
| CLI 原生 | 提供可安装 wheel/源码包，优先使用 uv tool install 或 pipx；setup 引导建目录、迁移 SQLite、创建管理员、设置模型与内置 worker | 提供 start/stop/status/logs/doctor、配置、备份恢复、升级迁移命令；可单独启动 server 或 worker |

CLI 原生完整主链路不依赖 Docker，不强制打开 Web 才能完成初始设置；设置完成后输出 Web 地址。Web onboard 与 CLI setup 共用初始化服务，重复执行不能覆盖数据库、重置管理员或轮换已有密钥。模型凭据通过隐藏输入或专用文件输入，不出现在进程参数和日志。

默认 Compose 一条命令启动 Web 与 worker；CLI 安装后 setup，再 start 即可启动两者。首期正式验证 Linux 与 macOS，Windows 原生适配另行评估，可使用 WSL2 的 Linux 路径。首次安装/构建需要公共网络；正常运行不访问内部依赖。前端静态资源随包提供，模型请求按用户配置访问。

首次启动展示短引导：

1. 用启动时的一次性初始化凭据创建管理员，设置管理员密码（避免远程空白实例被先到者占领）。
2. 配置模型，运行一次轻量能力检查；存储、端口和内置 worker 自动采用默认值。
3. 导入第一个 Skill，或用随附的小型合成样例体验审计与修复。

默认仅监听本机，页面中文，数据在单一 data 目录，并发 1，修复最多 3 轮，L1 默认，原包保留。对外共享时提供简单的域名/HTTPS部署说明，不自动暴露到公网。

命令名暂定 skill-mng；开发计划记录完整命令契约与两条部署验收。包名、镜像名尚未注册发布，方案中的命令是拟定接口，不能当作现成安装说明。

## 8. 仓库与实施顺序

在 独立项目目录 open-skill-mng（后迁入 lume-skill/skill-manage） 建立全新本地仓库，按白名单提取通用实现，不复制旧 Git 历史、业务数据、截图、发布包、内部配置和评测历史源码。

拟定目录：app/（Web/API/领域逻辑）、web/、worker/、skills/skill-deep-audit/、tests/、docs/、examples/、deploy/；data/ 为运行数据，不进入 Git。

开发按 P0–P6 顺序推进，依次完成基线与契约、SQLite/双部署、注册与权限、独立 worker、通用审计、自动修复、交付验收。任务、依赖、产物及完成条件统一见 [开发计划](DEVELOPMENT-PLAN.md)，全部属于本期范围。

因 CLI 安装设置、生命周期运维和一次性码接入明确列为正式能力，估算调整为 21–34 人日；这是规划范围，不含等待反馈或未知模型适配问题，完成基础部署和首个真实审计后校准，不作为交付日期承诺。

## 9. 首期完成标准

- 没有内部账号、Cookie、VPN 或公司服务，也可完成注册、审计、修复、复审和新版本下载。
- 上传与 URL 导入均有真实测试；非法压缩包与受限 URL 会被拒绝。
- 管理员与维护者权限由服务端校验，维护者不能修改别人的 Skill；worker 凭据无法取得管理员权限。
- worker 本机单独启动可执行任务；关闭浏览器不影响任务；重复领取、进程重启及迟到结果不产生重复有效版本。
- Docker Compose 和 CLI 原生分别在干净环境完成安装、初始化、启停及完整修复闭环；CLI 路径不安装 Docker 也能验收。
- 一次性授权码过期、复用、并发兑换和撤销均被正确处理；外接 worker 加入后无需用户填写其他平台凭据。
- 首期只有 SQLite 实现与迁移，配置不展示尚未支持的 PG/MySQL 选项。
- 有缺陷的合成 Skill 完成真实模型修复和独立复审；同时验证仍失败、超时、取消、轮次耗尽及模型未配置的情况。
- 审计/修复产物均绑定原包/候选摘要，失败、不确定或报告缺失不能通过 Gate。
